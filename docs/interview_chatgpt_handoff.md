## 2. 먼저 기억할 핵심

**자료상 가장 강한 성과는 공통 제어기와 SG90 매퍼를 하드웨어 의존성에서 분리하고, 같은 소스를 STM32와 Zynq에서 수정 없이 실행해 대표 입력의 계산 결과를 비교한 것이다.**

면접용 프로젝트명 후보:

> STM32·Zynq 간 공통 제어 소프트웨어 이식 및 검증

저장소 이름은 `Latency-Aware Target Control`이지만, 현재 구현에서 지연 예측·보상은 적용하지 않는다. `prediction_ms`는 0으로 설정된다. 프로젝트 이름만 보고 “지연 보상 알고리즘으로 추종 성능을 개선했다”고 설명하면 안 된다.

### 추천 스토리 방향 — 본인 경험을 확인하기 전의 제안

> 하드웨어가 바뀌어도 제어 로직을 재사용할 수 있도록 입력·시간·출력의 경계를 설계하고, 서로 다른 프로세서에서 동일한 소스를 실행해 그 경계가 실제로 유지되는지 확인한 경험.

이 방향에서는 다음 세 가지 판단이 중심이 된다.

1. 통신용 `TargetCommand`에서 제어에 필요한 좌표만 추출해 `TargetState`로 전달한다.
2. 시간 획득과 주기 실행은 플랫폼이 맡고, 공통 제어기는 전달받은 시간과 목표를 사용한다.
3. 조향각 계산, 액추에이터 매핑, 타이머 설정을 분리한다.

강조할 역량 후보는 **의존성 분리, 인터페이스 설계, 임베디드 통합, 검증 범위를 명확히 설명하는 능력**이다. 이는 코드 구조에서 도출한 해석이며, 실제 개발 동기·어려움·개인 기여는 나에게 확인해야 한다.

## 3. 프로젝트 개요와 환경

MATLAB/Simulink의 합성 탐지 데이터를 Linux C++ 프로그램으로 받아 UART 프레임으로 전달하고, STM32의 FreeRTOS 환경에서 제어·PWM 명령 생성까지 연결하는 프로젝트다. 이후 같은 공통 제어기와 매퍼를 Zynq PS의 FreeRTOS 환경에서도 실행했다.

| 구성 요소 | 역할과 확인된 범위 |
| --- | --- |
| MATLAB/Simulink + Automated Driving Toolbox | 가상 차량 시나리오와 합성 탐지 입력 생성 |
| Linux C++17 | UDP 수신, 위치 단위 변환, 명령 직렬화, UART 송신 |
| STM32F429I-DISC1 / Cortex-M4 | 기준 플랫폼. FreeRTOS, CMSIS-RTOS2, STM32 HAL 사용 |
| Zybo Z7-10 / Zynq-7000 PS / Cortex-A9 | 공통 소스 이식 플랫폼. FreeRTOS와 Xilinx BSP 사용 |
| 공통 C 코드 | 프로토콜, 조향 제어기, SG90 매퍼 |
| 개발 도구 | CMake/CTest, STM32CubeIDE/CubeMX, Vivado/Vitis 2022.1, Git |

Zynq에서 설명할 핵심은 **PS의 Cortex-A9에서 실행한 소프트웨어 이식**이다. 공통 제어 연산을 PL/FPGA로 가속한 프로젝트로 설명하지 않는다. 두 보드 모두 FreeRTOS이므로 여러 운영체제 간 이식까지 검증했다고 확대하지 않는다.

## 5. 전체 데이터 흐름

### 기존에 기록된 STM32 기준 경로

```text
Simulink 합성 탐지
  → UDP
  → Linux C++: 입력 수신·단위 변환·직렬화
  → UART 프레임 + CRC
  → STM32 런타임: 수신·프레임 검증·명령 복원
  → TargetState
  → 공통 조향 제어기
  → 조향각 [deg]
  → SG90 매퍼
  → PwmCommand [μs]
  → STM32 PWM 백엔드
  → TIM4_CH2 / PB7 설정
```

### 현재 소스의 수신·실행 구조 — 후속 보드 검증 필요

```text
UART ISR
  → UartRxByte 큐: 수신 바이트 + 연속성 식별값 epoch
  → 수신 태스크: 프레임 조립·CRC 검사·역직렬화
  → TargetState 큐
  → 주기 제어 태스크: 제어기 → 매퍼 → PwmCommand
      ├─ STM32: PWM 백엔드 호출
      └─ Zynq: 명령 계산·기록까지, 물리 PWM 백엔드 없음
```

현재 애플리케이션 태스크는 수신과 제어의 2개다. ISR은 별도 태스크가 아니다. 수신 태스크만 파서 상태를 수정하고, 제어 태스크만 제어기 상태를 수정한다.

## 6. 설계 선택과 그 의미

### 6.1 통신 형식과 제어 입력 분리

- 통신용 `TargetCommand`에는 `sequence`, `target_x`, `target_y`, `prediction_ms`가 있다.
- 제어용 `TargetState`에는 `int16_t x_cm`, `int16_t y_cm`만 있다.
- 런타임이 명령에서 좌표를 추출한다. 제어기는 UART 프레임, CRC, 순번, 예측 메타데이터를 알 필요가 없다.
- STM32 큐 이름은 과거 이름인 `targetCommandQueue`를 유지하지만, 현재 저장하는 항목은 `TargetState`다.

면접 설명의 초점: “어떤 통신으로 들어왔는지와 제어기가 계산할 입력을 분리했다.”

### 6.2 시간 획득과 주기 실행 분리

- `steering_controller_update_target(controller, target, now_ms)`로 목표를 갱신한다.
- `steering_controller_step(controller, now_ms)`으로 조향각을 계산한다.
- 공통 제어기는 HAL/RTOS 시각 API를 직접 호출하지 않는다. 플랫폼이 tick을 밀리초로 바꾸어 전달한다.
- 현재 설정은 제어 주기 20 ms, 목표 timeout 400 ms다.
- 목표 갱신 시각은 **제어 태스크가 목표를 반영한 시각**이다. 센서 측정 시각이나 통신 지연을 측정하는 타임스탬프가 아니다.

면접 설명의 초점: “비동기 입력 갱신과 주기 제어를 분리하고, 같은 제어기 코드에 각 플랫폼의 시간을 주입했다.”

### 6.3 제어기·매퍼·주변장치 백엔드 분리

- 제어기 출력은 조향각 `float`이며 단위는 도다.
- SG90 매퍼는 조향각을 `PwmCommand { period_us, pulse_width_us }`로 바꾼다.
- 매퍼는 SG90용 설정을 포함하지만 STM32 HAL, Zynq BSP, 타이머 레지스터에 의존하지 않는다.
- STM32 백엔드는 마이크로초 단위를 타이머 count로 변환해 ARR/CCR을 설정한다.
- 공통 코드 재사용 범위와 플랫폼별 재구현 범위를 명시적으로 나눈 구조다.

면접 설명의 초점: “하드웨어 독립적인 것은 공통 로직이고, 하드웨어 접근은 플랫폼별 백엔드에 남겼다.”

### 6.4 입력 이상과 미수신 처리

- 프레임 형식/CRC 오류는 통신 계층에서 거부한다.
- 좌표 `x_cm <= 0`은 제어기가 의미상 유효하지 않은 목표로 거부한다.
- 잘못된 목표는 마지막 유효 목표와 갱신 시각을 덮어쓰지 않는다.
- 새 유효 목표가 없으면 timeout 전까지 마지막 목표를 유지하고, timeout 이후에는 중립 조향각을 반환한다.
- 중립 복귀는 구현된 동작 정책이다. 차량 전체의 안전성을 검증했다는 의미는 아니다.

### 공통 제어기와 매핑

제어식은 Pure-Pursuit에서 착안한 목표 상대 기하학식이다.

```text
delta = atan(2 × L × y / (x² + y²))
```

`x`, `y`, `L`은 미터이며 결과를 도 단위로 변환한다. 현재 설정은 `L = 2.8 m`, deadband ±1°, 조향 제한 ±30°다. x 양수는 전방, y 양수는 좌측이고, 양의 조향각은 좌회전 방향이다. 이것만으로 경로 계획·차량 동역학·폐루프 추종 성능이 검증된 것은 아니다.

SG90 매핑은 현재 시험용 설정으로 -30° → 1200 μs, 0° → 1500 μs, +30° → 1800 μs다. 보간, 범위 제한, 장착 방향 반전에 대응하며 PWM 주기는 20000 μs다. 실제 서보 각도 보정은 완료된 것으로 기록되어 있지 않다.

### 후속 IRQ 구현의 설명 범위

- 바이트 큐는 기본 128항목, `TargetState` 큐는 4항목이다.
- 수신 태스크는 바이트 큐에서 대기한다. ISR은 바이트 수집과 큐 전달을 담당한다.
- 제어 태스크는 한 주기에 목표 큐에서 최대 4개를 꺼낸다. 목표 큐가 가득 차면 새 입력을 버리고 drop을 기록한다. 최신 값 덮어쓰기 큐로 설명하면 안 된다.
- 바이트 유실 또는 하드웨어 오류 시 `epoch`를 바꾼다. 수신 태스크는 꺼낸 바이트의 epoch가 달라지는 지점에서 미완성 프레임을 폐기해 유실 전후 바이트가 섞이지 않게 한다.
- 잡음/CRC 실패는 15바이트 sliding window를 이동하며 재동기화한다. `rejected_windows`는 거부된 창의 개수이며 손상된 패킷 개수와 같지 않다.
- 이 구조와 테스트 소스는 확인했지만, 실제 보드의 수신 신뢰성·CPU 사용률 개선·최대 처리량을 이번 자료에서 입증하지는 않는다.

## 8. 면접에서 사용할 수 있는 결과와 증거

### 8.1 대표 입력의 플랫폼 간 비교 — 기존 기록

| 항목 | STM32 | Zynq |
| --- | --- | --- |
| 비교 입력 | `TargetState {515, -97}` cm | 같은 고정 입력을 로컬 공급 |
| 조향각 | `-11.1881552°` | `-11188 mdeg`로 출력 |
| PWM 주기 명령 | `20000 μs` | `20000 μs` |
| PWM 펄스폭 명령 | `1388 μs` | `1388 μs` |
| 하드웨어 설정 관련 값 | `CCR2 = 1735 counts` | 물리 PWM 검증 대상 아님 |

`docs/images/stm32_zynq_validation.png`에서 위 입력·조향각·PWM 명령과 Zynq의 PASS 로그를 확인했다. 조향각은 **Zynq 로그의 표시 정밀도에서 일치**하고, 정수형 PWM 명령은 동일하다. 모든 입력, 모든 시간 조건, 실수 비트 단위 동일성까지 검증한 결과로 확대하지 않는다.

STM32의 문서화된 타이머 카운터 주파수는 1.25 MHz다. 따라서 20000 μs는 25000 counts, ARR은 24999이며, 1388 μs는 1735 counts다. 마이크로초와 count는 서로 다른 단위다. 레지스터 값은 실제 출력 핀의 파형 계측을 대신하지 않는다.

### 8.2 공통 소스 수정 0 LOC의 정확한 뜻

- 대상은 `common/src/steering_controller.c`와 `common/src/sg90_mapper.c`다.
- 두 보드 프로젝트는 Git에서 심볼릭 링크로 이 공통 파일들을 참조한다. 소스 복사본을 각 보드에서 따로 유지하는 방식이 아니다.
- Take 10 완료 커밋 `71d2f9b`와 Take 11-3 `a9bce86` 사이에서 두 공통 구현 파일의 diff는 없었다. Take 11-3부터 현재 기준 커밋까지도 이 두 파일의 diff는 없었다.
- README는 Zynq 이식 시 공통 소스 변경이 0 LOC였다고 기록하며, 기존 실행 캡처는 보드에서의 공통 파이프라인 실행 결과를 보여준다.
- **플랫폼 초기화, 태스크 구성, 드라이버, 빌드 설정까지 수정 없이 이식했다는 뜻은 아니다.**

### 8.3 통신과 timeout 기록

- `docs/images/e2e_validation.png`에는 Linux가 `(5.147 m, -0.972 m)` 부근 입력을 `(515 cm, -97 cm)` 명령으로 보내고, STM32가 같은 값을 큐로 전달한 캡처가 있다.
- 이 캡처는 이전 `TargetCommand` 큐 시점의 기록이다. 현재 `TargetState` 큐와 IRQ 구현의 실행 증거로 사용하지 않는다.
- README에는 `hold_before_timeout_seen = 1`, `timeout_neutral_seen = 1` 및 중립 시 0°, 1500 μs, CCR2 1875의 관찰 기록이 있다. 이 항목은 README의 과거 기록으로 구분한다.

### 8.4 테스트와 계측

- README에는 과거 호스트 CTest **7/7 통과**가 기록되어 있다. 이는 현재 전체 테스트 수나 이번 자료 작성 시의 실행 결과가 아니다.
- 현재 소스에는 프로토콜·제어기·매퍼 테스트 외에 스트림/epoch 경계, runtime support, STM32·Zynq IRQ 대역 테스트, 큐 할당 실패, Python 도구 테스트 등이 추가되어 있다.
- 호스트 대역 테스트는 실제 레지스터의 전기적 동작, RTOS 선점, 보드의 ISR 지연을 검증하지 않는다.
- 계측·내보내기 도구와 측정 절차는 존재한다. 양쪽 보드의 실측 실행시간, jitter, CPU 사용률 개선 수치는 이 자료에서 확인되지 않았다.
- `common_us`는 제어 step + SG90 매핑 구간이다. `work_us`는 STM32에서 PWM 백엔드까지 포함하지만 Zynq에는 그 백엔드가 없어, 둘을 그대로 CPU 속도 비교로 쓰면 안 된다.
- nominal 20 ms 주기 설정은 deadline 준수나 실시간 성능 보장의 실측 증거가 아니다.

### 90초 대본의 뼈대 — 완성된 개인 경험으로 단정하지 말 것

- 도입: 이 프로젝트가 해결하려던 문제와 본인 역할. `[내 경험 확인 필요]`
- 판단: 통신·시간·주변장치 의존성을 공통 제어기에서 분리한 이유. 코드 구조는 확인되었으나 개인 동기는 확인 필요.
- 구현: `TargetState` → 제어기 → SG90 매퍼 → `PwmCommand`라는 경계와 플랫폼별 런타임/백엔드.
- 검증: 두 공통 소스의 수정 없이 Zynq에서도 실행한 기존 기록, 대표 입력에서 약 -11.188°와 1388 μs 명령 비교.
- 마무리: 본인이 얻은 교훈과 지원 직무에 연결되는 역량. `[내 경험 확인 필요]`
